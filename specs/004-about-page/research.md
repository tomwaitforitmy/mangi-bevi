# Research: About Page

## 1. License extraction tool

**Decision**: Add `license-checker-rseidelsohn` (actively maintained fork of the
original `license-checker`) as a devDependency, invoked by a new Node script
`scripts/generate-license-data.js`, run from `scripts/prerelease.fish`.

**Rationale**: `license-checker`-family tools are the standard way to enumerate
npm dependency licenses (name, version, license identifier, path to the
package's LICENSE file) without hand-parsing `node_modules` per project. The
`--production` flag restricts to the actual runtime dependency tree (excludes
`devDependencies`), matching FR-004's "every dependency" scope — only code
that actually ships. The original `license-checker` package is unmaintained;
the `rseidelsohn` fork is the community-standard replacement.

**Alternatives considered**:
- Hand-rolled `node_modules` walk reading `package.json#license` — reinvents
  parsing SPDX expressions and dual-license fields license-checker already
  handles.
- `licensee` (Ruby gem) — wrong language ecosystem for a Node project.

## 2. License attribution filter

**Decision**: A pure function `scripts/lib/requiresAttribution.js` takes an
SPDX license identifier string and returns `true` unless it matches a small
excluded set: `Unlicense`, `CC0-1.0`, `WTFPL`, `0BSD` (case-insensitive,
handles simple `OR`/`AND` SPDX expressions by checking each component).
Anything not recognized (unusual/custom license text, no SPDX id) defaults to
**included** (fails safe toward showing more, not less — matches the
Clarifications decision to err toward the legally conservative side).

**Rationale**: Matches the spec's Clarifications answer #2 verbatim: include
everything with a copyright/notice-preservation clause, exclude true
public-domain-style licenses. Keeping this as an isolated, named exclusion
list (not a "known good" allowlist) means new/unusual licenses in future
dependencies default to being shown rather than silently dropped.

**Alternatives considered**: Allowlist of "known good" identifiers (MIT, BSD,
Apache-2.0, ISC, …) — rejected because an unrecognized future license would
silently be excluded, the opposite of the conservative default the spec asks
for.

## 3. Developer-hour estimate

**Decision**: A pure function `scripts/lib/estimateDevHours.js` —
`estimateDevHours(commitTimestamps, { sessionGapSeconds = 7200, firstCommitCreditSeconds = 1800 })`
— sorts timestamps, sums real gaps under the session threshold and a fixed
credit for each session's first commit, mirroring the standard "git-hours"
heuristic. Invoked by `scripts/generate-dev-hours-data.js`, which reads
`git log --pretty=format:%at` for `HEAD`, computes the estimate, and writes
the result alongside the session count and a generated-at timestamp.

**Rationale**: This is the same heuristic validated manually during
`/speckit-specify` (1264 commits → ≈423h / 329 sessions), already accepted by
the user as the documented methodology text for the Costs page (FR-008).
Extracting it into a pure, testable function satisfies Constitution Principle
I (Test-First) — the heuristic is exactly the kind of logic a unit test
should pin down (given a list of synthetic timestamps, assert the expected
hour total), independent of any real git repository.

**Alternatives considered**: Third-party `git-hours` npm package — adds an
external dependency for ~20 lines of logic the project needs full control
over (documented on-page, per FR-008); a hand-owned function is simpler and
matches Constitution Principle VI (Minimal Footprint).

**Constraint note**: The shipped app bundle does not include `.git` — this
estimate MUST be computed at release time (in `scripts/prerelease.fish`,
before `git add -A`) and stored as static generated data, never computed at
app runtime.

## 4. Where generated/static data lives

**Decision**:
- `data/generated/openSourceLicenses.json` — generated by
  `scripts/generate-license-data.js`, committed as part of the existing
  prerelease commit (already `git add -A`'d).
- `data/generated/devHoursEstimate.json` — generated by
  `scripts/generate-dev-hours-data.js`, committed the same way.
- `data/CostsConfig.js` — hand-maintained, following the existing `data/`
  convention (static config/constants, per root `CLAUDE.md`): the real
  monetary line items (Apple €396, Google €25, Claude Code €44), the fixed
  hourly rate (€25), and an `asOf` date the developer updates alongside the
  figures.

**Rationale**: Matches the existing `data/` directory's documented purpose
(static config/constants) without introducing a new top-level directory.
Splitting generated vs. hand-maintained data into separate files keeps the
prerelease script's write surface (the two `generated/` files) clearly
separate from what a human edits (`CostsConfig.js`), so the script can never
clobber a manually-entered monetary figure.

**Alternatives considered**: A single merged `data/AboutData.js` mixing
generated and manual content — rejected, makes it easy for a future edit (or
a bug in the generation script) to overwrite hand-entered monetary figures.

## 5. Screen/route placement

**Decision**: Flat files alongside existing siblings in
`app/(app)/profile/`, matching `account.js`/`friends.js`/`meals.js`/
`settings.js`'s existing flat naming (no nested subfolder):
`about.js`, `about-licenses.js`, `about-costs.js`. Each is a thin
`Stack.Screen` + screen-component wrapper using `GlobalBackIcon` for
`headerLeft`, exactly like `profile/settings.js`. `screens/AboutScreen.js`
replaces the inline version `<Text>` currently in `screens/ProfileScreen.js`
with a `MyButton` entry (mirroring the existing Account/Friends/Settings
buttons) that navigates to `/profile/about`.

**Rationale**: Root `CLAUDE.md` documents `screens/`/`components/` boundaries
as meaningful; matching the existing flat `profile/*.js` route-naming
convention is the smallest-footprint option (Constitution Principle VI) and
needs no `_layout.js` change — Expo Router auto-registers new files.

**Alternatives considered**: Nested `app/(app)/profile/about/index.js` +
`about/licenses.js` + `about/costs.js` folder — reads slightly cleaner as a
"section" grouping, but breaks from every existing sibling's flat pattern for
no functional benefit; rejected as unnecessary structural deviation.

## 6. License list rendering (long full-text content)

**Decision**: `screens/OpenSourceLicensesScreen.js` renders a `FlatList` of
collapsible rows (package name + license identifier always visible; full
license text expands on tap). All text still ships in the bundle and is
reachable with zero extra taps beyond "expand" — satisfies "full text
embedded, no external link-out" (Clarifications #1) while keeping the default
view scannable given ~60+ production dependencies.

**Rationale**: A always-expanded ~1MB of concatenated license text would make
the screen unusably long to scroll; collapsing by default is a rendering
choice, not a content-scope change — nothing is hidden behind a link, only
behind a local tap-to-expand.

**Alternatives considered**: Always-expanded flat text — technically compliant
but a poor reading experience at 60+ entries; rejected on UX grounds, not
required by any FR.
